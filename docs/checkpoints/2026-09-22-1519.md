## Decisions

- Задачи, зависимые от файлов текущего активного агента, откладываются до
  его завершения — выбор следующей пары всегда проверяется на пересечение
  файлов через анализ scope в самом finding'е, не наугад.
- Worktree, засеянный до мержа другой задачи, при обнаружении смешанного
  diff (часть — genuine правки текущей задачи, часть — stale-контент)
  разводится вручную по маркерному grep каждого файла (искать
  специфичные для НОВОЙ задачи символы/строки), а не мержится целиком —
  паттерн повторился минимум 4 раза в этой волне (S09 при мерже с S10-
  seed, S10 при мерже с S09-территорией, C04 при мерже с R03/R05-
  территорией, PERF-net-ipc при мерже с PERF-dir-территорией).
- Реальные баги, найденные при независимой верификации (не просто описанные
  агентом), чинятся на месте до мержа, не откладываются — так же, как и
  настоящие падения тестов.
- Rate-limit/watchdog-смерть агента (`exit_reason: "error"`) никогда не
  считается провалом задачи по умолчанию — всегда сначала независимый аудит
  worktree (compile + test + diff), решение мержить/перезапускать/чинить
  вручную принимается по факту, не по формальному статусу выхода.

## Lessons worth carrying forward (дополнение к прошлому чекпоинту)

- `find PATH1 PATH2 PATH3 -type f | xargs touch` (несколько путей в одном
  `find`, результат в `xargs touch` без `-I{}`) на этой Windows/MSYS bash
  среде ненадёжен и может склеивать путь директории с именем найденного
  файла без разделителя, создавая 0-байтовые файлы-мусор с явно неверными
  именами (`dirnamefilename.rs`). Стандартный безопасный способ теперь:
  `find ... -type f | xargs -I{} touch "{}"` (один `touch` на файл) — уже
  применяется во всех мержах с этого момента.
- `cp -r SRC_DIR DEST_DIR` когда `DEST_DIR` УЖЕ существует создаёт
  `DEST_DIR/SRC_DIR_basename/...` (вложенную копию), а не сливает
  содержимое — классическая семантика `cp -r`, но легко забыть в контексте
  повторных мержей. Правильная форма для слияния СОДЕРЖИМОГО одной
  директории в уже существующую: `cp -r SRC_DIR/. DEST_DIR/` (с точкой).
- Когда две параллельные `/wrush`-задачи независимо добавляют новые поля в
  один и тот же struct (например `PolicyInner`), обнаружить это можно
  только явным diff'ом обоих файлов против primary ПОСЛЕ мержа первой
  задачи — ни один из агентов не видит работу другого. Хэндлинг: читать
  primary-версию файла целиком, вручную (Edit) добавлять недостающие поля
  и конструкторную логику из второй задачи поверх уже смерженной первой,
  никогда не перезаписывать файл целиком одной из двух версий.
- Провайдерский usage-limit (5-часовой/9-часовой) — это ПОЛНЫЙ останов всех
  `rush run` до истечения окна; в отличие от единичного tool-timeout
  watchdog (который убивает один инструмент внутри одного агента), здесь
  ВСЕ параллельные и последующие запуски будут падать одинаково до сброса.
  При обнаружении такого лимита — прекратить запуск новых агентов, сообщить
  пользователю точное время сброса, ждать явного разрешения продолжить
  (в этом окне пользователь оба раза сбрасывал лимит вручную и просил
  продолжить).
