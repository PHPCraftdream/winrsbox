# Несколько winrsbox в одной папке: брокер на папку

Дата: 2026-09-28. Снимок исходников: `4882ebb`. Задача сессии: #110 (вторая часть).

**Статус: реализовано (2026-09-28), все этапы MP-0…MP-10 закрыты.** Этот
документ — история проектирования и фактических отклонений от плана, не
актуальная спецификация; для текущего поведения и границ модели угроз см.
`winrsbox/docs/THREATMODEL.md` (раздел «Multi-process broker (shared
folder)») и `winrsbox/README.md` (раздел «Multiple sessions in the same
folder»). Построчные записи «Готово (2026-09-28)» ниже фиксируют, что
реально сделано и чем это отличается от исходного плана на момент
написания — при расхождении с кодом доверять коду.

## Проблема

Второй `winrsbox` в той же папке делит state dir `<parent>\.winrsbox\<name>\` с первым:

- `policy.redb` открывается один раз на всю сессию (`Policy::open_or_create_with_layout`, `policy/src/domains/policy_impl.rs:77`). redb держит эксклюзивную блокировку файла всё время жизни `Database` — второй процесс получает `DatabaseAlreadyOpen` и не стартует. Та же ошибка у CLI-команд (`winrsbox rule add` и т. п., `launcher/src/cli/mod.rs:176`), пока идёт сессия.
- Короткий лок только на запись не решает задачу: горячий путь читает базу на каждое решение (`decide/mod.rs:801`, `decide/overlay.rs:395`), а `Policy` держит производные данные в памяти — `overlay_children_idx` строится при открытии и поддерживается только собственными `record_overlay`/`clear_overlay`, плюс кэш решений. Два процесса с общей базой расходятся: CoW-файл, созданный в A, невидим для B.

## Решение

**Один брокер на папку.** Базу, кэши и pipe-сервер держит один процесс. Остальные launcher'ы — клиенты брокера: у них своя консоль, свой токен, свой job, инъекция и запуск, но не своя база.

Координация — только примитивы ядра Windows; никаких lock-файлов и heartbeat для обнаружения смерти.

### Что важно о модели угроз

Токен гостя — `CreateRestrictedToken` без restricting SIDs, тот же SID пользователя, Medium (`contain/guest/build.rs:214`). DACL не отличает гостя от launcher'а. Поэтому все проверки «кто есть кто» опираются на **членство в job**, которое ядро не даёт покинуть (breakaway запрещён): гость всегда в job папки, launcher — никогда.

## Архитектура

### Объекты папки

| Объект | Примитив | Кто держит | Назначение |
|---|---|---|---|
| Роль брокера | Эксклюзивная блокировка `policy.redb` | брокер | Выборы. Кто открыл базу — тот брокер. Ядро снимает блокировку при смерти процесса. |
| Job папки | Безымянный Job Object без лимитов (кроме запрета breakaway), без `KILL_ON_JOB_CLOSE` | все launcher'ы (дубликаты хэндла) | Опознание гостей (`IsProcessInJob`), учёт «в папке ещё есть процессы». |
| Job сессии | Job Object с текущими лимитами (UI, память, `KILL_ON_JOB_CLOSE`), вложен в job папки | только свой launcher | Семантика сессии не меняется: смерть launcher'а убивает только его дерево. |
| Folder section | Именованная секция со случайным именем, DACL только чтение; хэндлы на запись есть только у launcher'ов (`DuplicateHandle` от брокера) | launcher'ы — RW, гости — R | Текущее имя pipe брокера, поколение, набор доверенных launcher'ов `(pid, create_time)`. |
| `broker.json` в state dir | Файл | пишет брокер | Точка входа для нового launcher'а: PID, create_time брокера, имя pipe, имя folder section. Не секрет: подключение проверяется ядром, а не знанием имени. |
| Pipe брокера | Случайное имя, `FILE_FLAG_FIRST_PIPE_INSTANCE` | брокер | IPC гостей и запросы `Attach`/`Ping` от launcher'ов. Случайное имя нельзя занять заранее. |

### Раскладка folder section (v1)

```
magic u32, version u32, generation u64 (растёт при каждой смене брокера)
broker_pid u32, broker_create_time u64
pipe_name [u16; 128]
launchers_len u32, launchers [(pid u32, create_time u64); 32]
```

Запись под seqlock (`generation` нечётное во время записи). Читатель повторяет чтение при несовпадении. Пишут только launcher'ы, и только брокер или присоединяющийся launcher о себе.

### Запуск launcher'а

1. `ensure_state` (идемпотентно; создание `sandbox.ktav` — через `CREATE_NEW`, без гонки двух процессов).
2. Попытка открыть `policy.redb`:
   - удалось → **брокер**: текущий путь запуска + создание job папки, folder section, pipe со случайным именем, `broker.json`;
   - `DatabaseAlreadyOpen` → **клиент**: шаг 3.
3. Клиент читает `broker.json`, открывает процесс брокера (`SYNCHRONIZE | PROCESS_QUERY_LIMITED_INFORMATION`), сверяет create_time и путь образа ядра с собственным `winrsbox.exe`, подключается к pipe и шлёт `Attach`.
4. Брокер проверяет клиента: не в job папки (ядро), тот же SID пользователя, путь образа совпадает с образом брокера. Затем дублирует в процесс клиента хэндлы job папки (`JOB_OBJECT_ASSIGN_PROCESS | JOB_OBJECT_QUERY`) и folder section (RW). Добавляет клиента в набор доверенных launcher'ов.
5. Клиент создаёт гостя как сейчас, но в session section записывает pipe брокера, имя folder section и `session_id`. Порядок job: сначала job папки, затем job сессии (вложение).

### Гость и хук

- При каждом подключении хук берёт имя pipe и набор доверенных серверов из folder section. Если folder section нет — используются значения из session section (совместимость).
- `verify_pipe_server_identity` (`hook/src/ipc/trusted_boot.rs:114`): вместо одного закреплённого PID — `(pid, create_time)` сервера входит в набор доверенных launcher'ов из folder section.
- `Hello` уже шлётся на каждом новом соединении (`ipc_client/mod.rs:461`, по MP-0). Менять нужно источник имени pipe: сейчас это `OnceLock` (`PIPE_NAME`), после failover хук стучался бы в старое имя.

### Допуск клиентов в pipe-сервере

`is_owned_client_pid` (`launcher/src/pipe_server/ownership.rs:218`) держится на одном `root_target_pid`. Замена: `IsProcessInJob(client, folder_job)` — факт ядра, сильнее родословной по PID. Трекер (Hello-контекст, create_time, глубина) остаётся источником контекста решения, но не допуска. Глубина для клиентов без записи в трекере (после failover) — обход родителей до процесса в трекере, иначе консервативное значение.

### Смена брокера (failover)

- Каждый клиент ждёт хэндл процесса брокера (`WaitForSingleObject` в отдельном потоке). Сигнал приходит в момент смерти, опрос не нужен.
- При сигнале клиент пытается открыть `policy.redb`. Кто открыл — новый брокер: redb сам восстанавливает базу после падения, кэши строятся из базы. Новый брокер поднимает pipe с новым случайным именем, обновляет folder section (`generation++`, broker, pipe) и `broker.json`.
- Проигравшие ждут обновления `broker.json` / `generation`, проверяют нового брокера (шаг 3) и повторяют `Attach`.
- Гости переподключаются к новому имени pipe из folder section. Бюджет хука (3 с на connect, 8 подряд неудачных вызовов) покрывает окно смены.
- Гости умершего брокера погибают вместе с его job сессии — как сейчас.
- Штатный выход: цель брокера завершилась, а в job папки ещё есть процессы. Брокер закрывает базу и выходит — дальше обычный failover. Терминал брокера не висит.

### Зависание брокера

Ядро здесь не поможет: брокер жив, держит базу и pipe.

- Клиент при подключении и затем раз в 5 с шлёт `Ping` с таймаутом 2 с.
- Таймаут → предупреждение в консоли клиента и в JSONL. Автоматически не убиваем: у брокера терминал пользователя, а зависание может оказаться долгой операцией.
- `winrsbox broker status` — брокер, поколение, клиенты, число процессов в job папки.
- `winrsbox broker restart` — `TerminateProcess` брокеру по проверенному хэндлу, дальше обычный failover.

### Логи и статистика

- `sandbox.log.jsonl`, `violations.log`, `hot-stats.json` пишет только брокер.
- События launcher'а-клиента уходят брокеру запросом `LauncherLog`.
- Статистика в брокере ведётся по `session_id` из `Hello`. Клиент в конце запрашивает `SessionStats` для итоговой сводки.

### CLI при идущей сессии

Команды `rule/regrule/netrule/mock/...` при `DatabaseAlreadyOpen` отправляют мутацию брокеру (`Attach`-аутентификация + `PolicyMutate`). Брокер применяет её и сбрасывает свои кэши. Без брокера — прямое открытие базы, как сейчас.

Аутентификация — `pipe_server::security::authenticate_attach_client` (чистое ядро `authenticate_attach_impl` + продакшен-обвязка): процесс клиента открывается **один раз** с `ATTACH_CLIENT_ACCESS = PROCESS_QUERY_LIMITED_INFORMATION \| PROCESS_DUP_HANDLE \| SYNCHRONIZE`, и на этом единственном хэндле проверяются по очереди — `launcher_pid == GetNamedPipeClientProcessId`, `launcher_create_time` == живой create_time (0 не проходит), `!FolderJob::contains` (гость всегда в job папки, launcher — никогда; неопределённый результат `contains` трактуется как «в job», fail-closed), SID (`token_string_sid_for_process`, обобщение `current_user_string_sid` на чужой хэндл) совпадает с SID брокера, путь образа (`ownership::image_path_from_handle`, тот же приём — обобщение `query_process_image_path`) совпадает с `std::env::current_exe()` по S11-фолду. На успехе — `try_complete_attach` (`main/broker.rs`): `FolderJob::duplicate_into`/`FolderSectionWriter::duplicate_into` (RW), `add_launcher`, снимок `generation`, запись `Resp::Attached`; любой сбой на любом шаге — полный откат (уже продублированный в клиенте хэндл закрывается через `DuplicateHandle(..., DUPLICATE_CLOSE_SOURCE)` — стандартный приём удалённого закрытия чужого хэндла), включая ошибку самой записи ответа (`remove_launcher` + откат обоих хэндлов). `FolderSectionWriter` (`main/broker.rs`) оборачивает `FolderSection` в `Mutex<()>` — несколько воркеров accept-пула могут одновременно завершать `Attach` и `remove_launcher`, а секция требует единственного писателя.
