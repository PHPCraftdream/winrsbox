# XA: ревью безопасности и производительности winrsbox

Дата начала: 2026-09-20. Завершение: 2026-09-21. Проверенный снимок: `8eb9f211a72ead1a7d4deb50f97b26acdfaa4ca4`.

## Вывод

Проект заметно усилен последними коммитами, но уязвимости остались. Есть несколько конкретных путей записи на хост через обычные Windows API, без собственной инструкции `syscall`. Поэтому сейчас winrsbox пригоден как экспериментальный слой контроля для знакомых инструментов, но не как единственная граница защиты от произвольного кода агента, зависимостей и build scripts. `--guard static` этого вывода не меняет: он добавляет полезные ограничения динамического кода, но ошибки файловой авторизации, IPC и конфигурации потомков от этого не исчезают.

Главные исправления: правильно учитывать `MAXIMUM_ALLOWED`; сделать конфигурацию и запуск потомков доверенным протоколом; устранить выполнение гостевых обработчиков исключений при отключённых хуках; проверять и исполнять один и тот же снимок файлового запроса; разделить физические overlay разных проектов. Оптимизации тоже есть, причём наиболее значимые связаны с лишними полными обходами каталогов, повторными IPC/транзакциями и жизненным циклом соединений, а не с заменой одного аллокатора другим.

## Область и метод

- Изучены 28 коммитов, достижимых из проверенного HEAD, по `git log --since='2026-09-13' --until='2026-09-22'`: их история, состав изменений и итоговые затронутые пути. В этом снимке последние коммиты датированы 20 сентября; коммитов 21 сентября в его истории нет.
- Проверены launcher, IPC, policy, файловые/реестровые/сетевые хуки, memory/injection/process guards, session section, UI, Job Object, npm installer и состав CI. Старые аудиты использованы как список проверок; исправленные находки не перенесены автоматически в новый список.
- Ревью выполнено в отдельном worktree по зафиксированному HEAD. Незакоммиченный рефакторинг основного checkout и другие рабочие ветки в выводы не включены. Все `file:line` ниже относятся именно к этому снимку; пути относительно корня репозитория.
- Это статическое ревью с трассировкой путей исполнения и сверкой существенной Windows-семантики по документации Microsoft. Exploit-процессы, нагрузочные сценарии, сборка и тесты в этом ходе не запускались. Единственное изменение — этот отчёт; он не является отчётом об успешном pentest или о прохождении тестов.
- «Подтверждено кодом» означает, что условие, разрешающая ветка и опасная операция прослежены в исходниках. Это отличается от воспроизведения на конкретной версии Windows. Для гипотез прямо указаны недостающие проверки.

Приоритеты: **P0** — блокирует использование как защитной границы и требует первоочередного исправления; **P1** — существенный дефект изоляции или явно обещанной защиты; **P2** — корректность, надёжность, ресурсы или производительность. Уверенность в кодовом механизме указана отдельно от приоритета.

## Подтверждённые дефекты безопасности

### S01 — P0: MAXIMUM_ALLOWED выдаёт write-capable handle реального файла по read-решению

**Уверенность: высокая, подтверждено кодом и контрактом Windows.** Режимы: `scan/full/static`. Предусловие: существующий доступный пользователю на запись файл вне project_root, без materialized overlay; чтение разрешено политикой. Это обычный исходный случай для файлов пользователя.

`winrsbox/hook/src/hooks.rs:263` прямо исключает `MAXIMUM_ALLOWED` из `is_write_access`; маска на строке 269 его не содержит. `NtCreateFile(..., MAXIMUM_ALLOWED, FILE_OPEN, ...)` и `NtOpenFile` поэтому запрашивают `write=false` (`fs_hooks.rs:289`, `fs_hooks.rs:689`). Policy разрешает чтение реального файла, а passthrough передаёт исходный `desired_access` ядру (`fs_hooks.rs:412`). Ядро выдаёт все права, разрешённые DACL, включая запись. Последующая запись через этот handle не проходит новую файловую авторизацию: `NtWriteFile` не перехвачен.

**Воздействие:** изменение существующего файла хоста, в том числе файла под правилом `read: passthrough / write: deny`. Защита каталога установленной песочницы также не спасает от этой формы открытия. Создать из ничего новый файл таким способом не требуется: атакующий выбирает существующий writable target.

**Исправление:** считать `MAXIMUM_ALLOWED` потенциальной записью либо выдавать лишь явно ограниченные read-права, если принято read-решение. Стоимость CoW нельзя уменьшать выдачей реального write handle. Unit-тест `hooks.rs:2753`, закрепляющий `!is_write_access(MAXIMUM_ALLOWED, FILE_OPEN)`, имеет неверный security oracle и должен измениться вместе с кодом.

Основание: [Microsoft: Requesting Access Rights to an Object](https://learn.microsoft.com/en-us/windows/win32/secauthz/requesting-access-rights-to-an-object).

### S02 — P0: доверенная section не защищает конфигурацию и bootstrap потомков

**Уверенность: высокая.** Предусловие: агент может менять своё окружение и создавать потомков — базовая возможность кодер-агента.

Есть несколько независимых частей одной нарушенной границы доверия:

1. `install_hooks()` сначала заполняет `PIPE_NAME`, `DLL_PATH`, `SANDBOX_CWD`, `SANDBOX_ROOT` из env (`hooks.rs:2382`). Только затем загружает section (`hooks.rs:2424`). Загрузка использует `OnceLock::set` с игнорированием результата (`ipc_client.rs:187`), поэтому доверенная section **не заменяет** уже принятые гостевые значения. Spawn-gate проверяет часть guard-переменных, но не `FS_SANDBOX_PIPE`, `FS_SANDBOX_DLL`, `FS_SANDBOX_CWD`, `FS_SANDBOX_ROOT` (`hooks.rs:1735`). Клиент не проверяет идентичность сервера pipe (`ipc/src/lib.rs:310`). Родитель может запустить ребёнка с pipe атакующего, который отвечает `Decision::Passthrough`; файловые операции ребёнка пойдут на реальный диск. Подмена `DLL` влияет на инъекцию следующего поколения.
2. Section содержит `guard`, `allow_rwx`, `disable_hooks` (`ipc/src/lib.rs:49`), но `try_load_session_config_from_section()` эти поля не применяет. Guard заново читается из env (`hooks.rs:2453`). Отсутствующие переменные разрешены gate как «безопасные defaults» (`hooks.rs:1727`), хотя default `full` слабее родительского `static`. Кроме того, gate принимает регистр `FULL/STATIC`, а исполнители сравнивают строки с `full/static` буквально (`hooks.rs:1715`, `hooks.rs:2620`, `memory_guard.rs:154`): сравнение на входе и использование не имеют единой семантики.
3. Для потомка успешная инъекция означает только успешную постановку APC `LoadLibraryW` (`inject.rs:169`, `inject.rs:200`), а не загрузку hook.dll и установку guard. После этого его возобновляют (`hooks.rs:2205`, `hooks.rs:2233`). Отдельного per-child bootstrap acknowledgement нет. Наследование root init event не превращает его в acknowledgement конкретного ребёнка.
4. `process_tracker::mark_spawned` выдаёт процессу статус owned до инъекции (`hooks.rs:2188`), а право `WriteProcessMemory`/`VirtualProtectEx` в owned child остаётся доступным гостю (`memory_guard.rs:1280`, `memory_guard.rs:1553`, `memory_guard.rs:1620`). В частности, запросив `CREATE_SUSPENDED`, родитель получает ребёнка до исполнения APC и может изменить его env/параметры загрузки после всех проверок, затем возобновить. Проверка caller-supplied env до syscall также не защищает его от конкурентной записи между проверкой и копированием ядром.

**Воздействие:** потомки с подменённым policy server, отключёнными хуками или не загруженной hook.dll. Процесс может остаться в Job, но файловая/реестровая изоляция уже отсутствует. Это escape из CoW, даже без выхода из Job.

**Исправление:** все security-поля брать из одной launcher-authored конфигурации, fail-closed при её отсутствии; env оставить только транспортом идентификатора. Использовать типизированный guard enum. Создание, подготовку и подтверждение защиты ребёнка завершать до передачи guest-коду действующих mutation handles; убрать бессрочную привилегию на запись в owned child. Проверять сервер IPC и устанавливать отдельное подтверждение для каждого ребёнка. Эти меры должны закрывать и намеренно очищенное окружение, и запрос `CREATE_SUSPENDED`, а не только `SetEnvironmentVariable` с известным kill switch.

### S03 — P0: исключение внутри memory guard запускает guest VEH с выключенной защитой

**Уверенность: высокая в кодовом механизме; live PoC не запускался.** Режимы: все, в которых установлен memory guard. Предусловие: нативный код может зарегистрировать vectored exception handler.

`hook_nt_protect_virtual_memory` устанавливает `anti_rec` (`memory_guard.rs:1276`), затем непосредственно читает caller-controlled диапазон через `from_raw_parts` и scanner (`memory_guard.rs:1297`). Полноценной fault-safe копии диапазона здесь нет. Можно передать committed `PAGE_NOACCESS` non-module страницу для перехода в executable: хук читает её **до** вызова ядра и проверки, допустима ли вообще операция. Возникает access violation. Windows вызывает guest VEH до раскрутки стека; RAII `Guard` в этот момент ещё существует. Вызов файлового API из VEH видит установленный TLS-флаг и проходит через `call_original` (`anti_rec.rs:99`, `fs_hooks.rs:179`). Вредная запись может завершиться до дальнейшего завершения процесса.

**Воздействие:** обычные API работают без FS/registry/process guards из гостевого обработчика. `static` не предотвращает само чтение hook-кодом недоступной страницы; для handler достаточно заранее скомпилированного кода.

**Исправление:** не разыменовывать hostile память, находясь в глобальном окне обхода хуков. Применять контролируемое копирование, которое возвращает ошибку вместо вызова guest exception handlers, минимизировать окно bypass и пересмотреть саму модель авторизации по TLS-флагу. Простое `VirtualQuery` перед чтением недостаточно против другой нити, меняющей защиту страницы. Комментарий `anti_rec.rs:78` уже признаёт этот класс, но текущая реализация memory scan не исполняет заявленную предпосылку.

Более общий предел: сам TLS-флаг находится в адресном пространстве гостя. Знание номера слота позволяет гостю установить его через `TlsSetValue`; секретом такой индекс быть не может. Это дополнительная причина не объявлять in-process hooks непроницаемой границей против произвольного нативного кода.

Основания: [Microsoft: Vectored Exception Handling](https://learn.microsoft.com/en-us/windows/win32/debug/vectored-exception-handling), [Microsoft: TlsSetValue](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-tlssetvalue).

### S04 — P1: файловый TOCTOU закрыт лишь после повторного чтения уже проверенного запроса

**Уверенность: высокая.** Предусловие: две гостевые нити и изменяемый буфер NT-вызова; для passthrough выбирается разрешённый путь в проекте.

`resolve_for_hook()` сохраняет абсолютную исходную строку лишь для RootDirectory-relative формы; для absolute возвращает `pre_resolved=None` (`hooks.rs:382`, `hooks.rs:481`). Policy проверяет строку, затем `HookedAttrs::copy_passthrough_inner()` снова читает исходный `ObjectName` (`hooked_attrs.rs:200`, `hooked_attrs.rs:283`; вызов после `decide` в `fs_hooks.rs:389`). Копирование после проверки не гарантирует, что копируются проверенные байты. Конкурентная подмена строки/указателя между ними позволяет проверить путь проекта, а открыть внешний.

Другие проявления: absolute rename при `RootDirectory=NULL` сразу вызывает original с гостевым буфером (`fs_metadata_guard.rs:471`); `NtDeleteFile` passthrough передаёт исходные attrs (`fs_metadata_guard.rs:1019`). Для rename относительный случай уже перестраивает абсолютный путь, но абсолютный остался без такого связывания.

**Воздействие:** запись, перенос или удаление по адресу, на который policy не давала разрешения.

**Исправление:** один owned snapshot всего значимого запроса **до** классификации; и decision, и syscall должны пользоваться им. Снимок должен включать не только имя, но и флаги/RootDirectory и применимые поля rename. Отдельно сохранить различие физического overlay-пути и виртуального имени — это не повод перечитывать гостевой буфер.

### S05 — P1: существующий junction/symlink в passthrough-дереве выводит запись за границу

**Уверенность: высокая при указанном предусловии.** Предусловие: до запуска внутри проекта уже есть junction/symlink на внешнее writable дерево либо hard link на внешний файл. Это может быть обычное состояние рабочей копии; создавать ссылку через уже установленные хуки не требуется.

`Policy::compute` разрешает всё под строковым `project_root` раньше проверки правил (`decide.rs:1021`). Passthrough open не запрещает traversal существующих reparse points (`fs_hooks.rs:389`). Проверка итогового объекта удалена; это явно записано в `hooks.rs:1181`. Запрет новых `FSCTL_SET_REPARSE_POINT` и hardlink API не обезвреживает существующие aliases. Например, `<project>/linked/file` может физически лежать вне проекта, а файловый handle получит write-доступ к реальному target.

**Воздействие:** host write вне разрешённого дерева. Для hard link путь остаётся в проекте, но меняется тот же файловый объект, доступный снаружи.

**Исправление:** задать политику существующих aliases и исполнять её через handle-based resolution/no-follow, до операции с побочным эффектом. При поддержке junction сравнивать авторизуемый конечный объект/том; для hard links учитывать общность объекта. Простая post-open проверка слишком поздняя для `OVERWRITE`/truncate. Повторный `symlink_metadata` перед `copy` (`hooks.rs:1328`) также не является атомарным устранением TOCTOU и не проверяет промежуточные компоненты пути.

Основания: [Microsoft: Reparse Points](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-points), [Microsoft: Hard Links and Junctions](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions).

### S06 — P1: scan пропускает исполняемые байты и не доказывает отсутствие direct syscalls

**Уверенность: высокая.** Предусловие: нативный код/специально сформированный PE. Для первого варианта достаточно `full/scan`; для PE-варианта динамическая генерация кода не нужна.

- **Округление VirtualProtect:** сканируется ровно переданный диапазон `addr,size` (`memory_guard.rs:1297`), а Windows меняет защиту всех затронутых страниц. Запрос перехода RW→RX для одного чистого байта разрешает исполнение всей страницы, в том числе несканированных байтов рядом. Этот обход не требует прямого RWX allocation и не является известным исключением для JIT.
- **Linear sweep:** `find_direct_syscalls` декодирует от нулевого смещения (`policy/src/scan.rs:59`). Байты, признанные immediate, могут быть реальной точкой перехода исполнения. Собственный тест `mov_with_immediate_containing_syscall_bytes_no_hit` демонстрирует именно различие между «не является инструкцией выбранного разбора» и «не может быть исполнено».
- **Только секция с именем `.text`:** PE helper ищет это имя, а не все `IMAGE_SCN_MEM_EXECUTE` sections (`policy/src/scan.rs:113`). Чистая `.text` плюс дополнительная executable section остаётся вне pre-launch scan и соответствующего DLL scan (`memory_guard.rs:1451`).
- **64 MiB в sibling-путях:** cap удалён для runtime region scan, но остался в root pre-launch (`launcher/src/inject.rs:116`) и child scan (`hooks.rs:1967`). Хвост большой `.text` не проверяется.
- **Время проверки:** RW-байты читаются до защиты RX; другие нити могут изменять их между сканированием и syscall. SEC_IMAGE mapping сначала появляется в процессе, затем проверяется (`memory_guard.rs:1410`). Нужен отдельный контроль того, когда исполнение становится возможным.

**Воздействие:** обход user-mode изоляции после пропущенного syscall-кода. Kernel Job остаётся самостоятельным ограничением, но не возвращает файловый CoW.

**Исправление:** сначала исправить округление, покрытие всех executable sections и capped siblings; определить, какую гарантию действительно предоставляет scanner. Для строгого запрета произвольных точек входа linear sweep недостаточен. Политика «обнаружили syscall — завершаем» разумна, но не равна механизму «ни один syscall вне доверенного пути не выполнится». Нельзя считать JIT-совместимость доказательством необходимости разрешать прямые syscalls, а ACG — доказательством невозможности использовать уже существующие инструкции.

Основания: [Microsoft: VirtualProtect](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualprotect), [Microsoft: PROCESS_MITIGATION_DYNAMIC_CODE_POLICY](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-process_mitigation_dynamic_code_policy).

### S07 — P1: проекты с одинаковым basename разделяют физический C: overlay

**Уверенность: высокая.** Предусловие: два разных проекта на диске, отличном от C:, с одинаковым последним компонентом имени, при обычном общем `LOCALAPPDATA` пользователя.

Для дополнительного C: root берётся только `project_root.file_name()` (`launcher/src/main.rs:544`), затем строится `%LOCALAPPDATA%/.winrsbox/<basename>/workdir` (`main.rs:549`). Полный project path и session id не входят в ключ. Основные policy DB при этом разные. Физический fallback проверяет файлы непосредственно в общем mirror (`decide.rs:1119`), даже если в DB этой песочницы нет соответствующей записи.

**Воздействие:** чтение и перезапись C: overlay другой песочницы, смешивание зависимостей/конфигурации, не только гонка запуска. Случайное имя session section этот storage collision не исправляет. Повторные запуски также видят оставшиеся данные другого одноимённого проекта.

**Исправление:** стабильный уникальный идентификатор по полному каноническому project identity либо явно выделенный sandbox id; для независимых сессий — отдельный session component. Все roots, DB, регистрируемые пути и протокол должны ссылаться на этот identity. Дополнительный C: root создавать с тем же no-reparse контрактом, что основной state root; сейчас там обычный `create_dir_all` (`main.rs:561`).

### S08 — P1: включённая сеть не обеспечивает заявленное ограничение дерева

**Уверенность: высокая.** Предусловие: `network: guarded`, `netrule` или `--block-localhost`; default network-off сам по себе не объявляется багом — это явно принятое поведение.

`net_hooks` перехватывает только `ws2_32!connect` (`net_hooks.rs:166`). `WSAConnect`, `ConnectEx`, `sendto` и прямой socket IOCTL остаются вне этого решения. WFP устанавливает фиксированные private/SMB блокировки только по APP_ID корневого executable; произвольные `netrule` в WFP не транслируются (`main.rs:953`). Поэтому, например, deny для публичного адреса обходится другой обычной socket API. Дети с другим image path не получают root WFP-фильтры, а userspace `NetDecide` без явных правил разрешает любой адрес (`pipe_server.rs:1200`). Само `network: guarded` не запрещает даже обычный `connect` ребёнка к RFC1918.

Есть дополнительные сужения:

- `FS_SANDBOX_BLOCK_LOCALHOST` перечитывается на каждом `connect` (`net_hooks.rs:89`); гость может удалить его. WFP у другого image-потомка отсутствует.
- APP_ID — путь executable, а не PID или Job. Фильтр затрагивает также запущенные вне песочницы процессы с тем же image path; разные песочницы одного executable могут влиять на сеть друг друга.
- При отказе WFP open/add launcher продолжает запуск (`main.rs:960`, `main.rs:1001`). `.bat/.cmd` вообще пропускают WFP, причём предупреждение скрыто за verbose (`main.rs:940`), хотя SECURITY обещает сообщение на stderr.
- Hostname-правила не соответствуют реальному числовому адресу `connect`; это признано в `pipe_server.rs:1203`. Allow + catch-all deny не образуют allowlist: любой matching deny выигрывает (`pipe_server.rs:1217`). Это требует ясной пользовательской семантики.

**Воздействие:** обход включённого egress control и lateral movement; одновременно нежелательные блокировки несвязанных процессов с тем же executable.

**Исправление:** привязка к реальной identity дерева и одинаковая policy для всех путей сетевого ввода-вывода; при обязательном guarded-режиме fail-closed на отсутствии требуемого kernel enforcement. Если пока поддерживается лишь частичный userspace контроль, называть и показывать именно эту возможность. Параметры сети должны участвовать в доверенной конфигурации S02.

Основание APP_ID: [Microsoft: Filtering condition identifiers](https://learn.microsoft.com/en-us/windows/win32/fwp/filtering-condition-identifiers-).

### S09 — P1: IPC удостоверяет отправителя, но доверяет присланным identity других процессов

**Уверенность: высокая.** Предусловие: процесс уже является законным клиентом pipe.

`Hello.pid` сверяется с kernel client PID, однако `Hello.exe_path` остаётся гостевой строкой и обновляет `ProcInfo.exe_lower` (`pipe_server.rs:1471`, `pipe_server.rs:1483`). Это позволяет подменить контекст `when.exe`. `SpawnedChild.child_pid` не проверяется на фактическое родство/членство в Job: server запрашивает время создания любого указанного процесса и заносит его в доверенную таблицу (`pipe_server.rs:1500`, `pipe_server.rs:1532`). Последующий gate считает такой живой fingerprint owned (`pipe_server.rs:347`). Так что fingerprint защищает от PID reuse, но одновременно «заверяет» чужой PID, указанный атакующим. `RegisterChild` также принимает любой PID (`pipe_server.rs:1654`).

Запросы `Decide` разрешены до `Hello` с `depth=None, exe=None` (`pipe_server.rs:1549`); depth без контекста трактуется permissively в части правил (`decide.rs:177`). Кроме того, depth — `u8`, и вычисление `parent_depth + 1` на строке 1541 не проверяет переполнение. Поддельные цепочки могут влиять и на контекст, и на устойчивость launcher.

**Воздействие:** обход exe/depth-scoped правил, расширение множества клиентов, которым доверяет server, отравление supervision и учёта. Поддельный registration сам по себе не выводит процесс из Job — это не приписывается находке.

**Исправление:** получать image path и родство/Job membership из доверенной стороны; неизвестного ребёнка не повышать до trusted только по сообщению. Обязательный handshake/state machine перед другими запросами. Depth вычислять проверяемо, с достаточным диапазоном; guest-reported identity оставить только диагностикой.

### S10 — P1: успешная инициализация допускает отсутствующие guard и kernel mitigation

**Уверенность: высокая в fail-open ветках; вызвавший их deployment-сценарий не воспроизводился.** Предусловие: ошибка загрузки модуля, установки detour или применения mitigation.

`install_hooks()` буферизует ошибки registry, network, ALPC, UI, service, shell, system и продолжает (`hooks.rs:2494`, `hooks.rs:2523`), после чего сигнализирует init event и возвращает `Ok` (`hooks.rs:2563`). Некоторые sibling API устанавливаются best-effort внутри модулей: например, registry `install_best_effort!` (`reg_hooks.rs:1095`) и legacy process creation (`proc_guard.rs:1153`). Все результаты `SetProcessMitigationPolicy`, включая `ProhibitDynamicCode` и `MicrosoftSignedOnly`, игнорируются (`hooks.rs:2625`, `hooks.rs:2636`).

**Воздействие:** оператор получает успешный запуск выбранного guard tier, хотя часть его защиты отсутствует. Для `static` это особенно существенно: create-time bootstrap специально снимает запреты, а успешность повторного включения после инъекции не удостоверяется.

**Исправление:** обязательный набор enforcement capabilities для каждого tier; отказ запуска или явный согласованный degraded tier при невозможности его установить. Init acknowledgement должен содержать фактический результат, а не означать лишь достижение конца `install_hooks`. Проверять mitigation через код возврата и применимые query API.

### S11 — P1: не-ASCII регистр не совпадает с identity файлов Windows

**Уверенность: высокая для обычного case-insensitive NTFS; специальные case-sensitive каталоги требуют отдельной модели.** Предусловие: deny/mock/overlay path содержит буквы вне ASCII, у которых есть регистровая пара.

Основная нормализация стала ASCII-only, а literal matcher сравнивает байты (`policy/src/path.rs:557`). Например, путь правила с `секрет` и запрос с `СЕКРЕТ` дают разные policy keys, хотя стандартный Windows open относится к одному объекту. Это отличается от устранённой ошибки несовместимости `to_lowercase` и `ensure_lower`: одинаковое ASCII-folding везде ещё не означает совпадение с filesystem case equivalence. Дополнительно часть hook записей whiteout/overlay всё ещё вызывает Unicode `to_lowercase` (`fs_hooks.rs:321`, `fs_hooks.rs:448`, `fs_metadata_guard.rs:672`).

**Воздействие:** read-deny/mock можно обойти изменением регистра; overlay и whiteout могут расходиться между вариантами одного имени. Нельзя обещать секретность правил на не-ASCII путях.

**Исправление:** определить один Windows-compatible, UTF-16-aware identity key, учитывающий фактическую case-sensitivity, и применять его на всём пути записи/чтения/сравнения. Не заменять это произвольным Unicode lowercase: оно тоже не равно NTFS-семантике. Добавить тесты cyrillic case pairs, surrogate pairs и case-sensitive directory.

### S12 — P1: npm source pin устанавливает дерево до security fixes

**Уверенность: высокая.** Предусловие: установка пакета обычным внешним source-build путём, а не dev-fast-path внутри monorepo.

`npm/winrsbox/package.json:11` закрепляет `9d73d34edb321a50fa4c2b7eefda355b34cdccfc`. Это 19 сентября, до `cfb00bd`, `85088aa`, `1629161`. Installer действительно переключается на этот commit и проверяет SHA (`scripts/install.js:119`, `scripts/install.js:135`). Сверка `git show` подтверждает, что его `record_overlay` ещё сохраняет произвольный guest overlay. Фиксы текущего HEAD в такой сборке отсутствуют.

**Воздействие:** пользователь собирает «текущий» installer, но получает старую уязвимую реализацию; SHA-256 integrity manifest затем корректно удостоверяет именно старые байты. Pinning полезен для воспроизводимости, но правильный pin должен указывать на проверенный релизный снимок.

**Исправление:** перевести source pin на принятый исправленный commit в рамках согласованного релиза, проверять соответствие package→source→artifact в CI. Отдельно проверить dev-fast-path (`install.js:88`), который сознательно собирает локальное дерево без этой проверки. В данном ревью pin и версии не менялись; состояние опубликованного npm registry не проверялось.

### S13 — P1: NtCreateKey с KEY_READ всё ещё создаёт реальный ключ под Cow

**Уверенность: высокая.** Предусловие: пользователь имеет право создавать ключи под выбранным HKCU-prefix, policy возвращает Cow; запрошен read-only handle.

В `nt_create_key_action` только `Mode::Deny` для read-only перенаправляется в `NtOpenKey`. `Mode::Cow` + `KEY_READ` идёт в `Proceed` (`reg_hooks.rs:473`) и в реальный `NtCreateKey` (`reg_hooks.rs:603`). Право на будущие записи через возвращаемый handle не отменяет побочный эффект самой операции create-or-open. В результате гость создаёт реальные ключи в области, где ожидается overlay/отказ от host writes.

**Воздействие:** изменение registry хоста, например создание нового ключа в HKCU\Software под CoW policy. Это более узкая возможность, чем произвольная установка значения; последующий `NtSetValueKey` всё ещё проверяется.

**Исправление:** `OpenExistingOnly` также для Cow/read-only либо полноценное virtual-key creation. Исправить тест, закрепляющий Cow+KEY_READ→Proceed (`reg_hooks.rs:1641`). Отдельный функциональный пробел: обычные `NtOpenKey`, `NtQueryValueKey`, `NtEnumerateValueKey`, `NtEnumerateKey` не перехвачены (`reg_hooks.rs:9`, `reg_hooks.rs:484`). Поэтому read-deny, registry mock и merged overlay reads нельзя считать работающей runtime-функцией только потому, что их умеет policy crate; документация должна показывать фактическую поддержку.

Основание: [Microsoft: ZwCreateKey](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-zwcreatekey).

## Подтверждённые дефекты корректности и надёжности

### C01 — P2: merged directory enumeration теряет и повторяет записи

**Уверенность: высокая.** `append_overlay_entries` при заполнении буфера просто отбрасывает текущую и все следующие extras (`dir_filter.rs:332`). Per-handle cursor для extras отсутствует. На каждой реальной странице extras загружаются заново, а дедупликация учитывает только текущий буфер (`dir_filter.rs:1093`). При `STATUS_NO_MORE_FILES` функция возвращается, не выдавая оставшийся overlay (`dir_filter.rs:995`). Если страница состоит только из скрытых записей, возвращается конец всего перечисления (`dir_filter.rs:1043`), даже когда следующая страница содержит видимые файлы.

`return_single_entry` и `restart_scan` не передаются в `process_dir_output` (`dir_filter.rs:1204`), поэтому добавление extras может нарушать запрос одной записи. Search pattern перечитывается из параметра текущего вызова; состояние первоначального поиска не сохраняется, хотя Windows сохраняет маску для последующих вызовов на handle. В синтетическом успехе после `STATUS_NO_SUCH_FILE` меняется Information и return value, но не `IoStatusBlock.Status` (`dir_filter.rs:977`); аналогичное расхождение есть на только-hidden EOF.

**Воздействие:** неполные/дублированные результаты `find`, package managers, build tools; в крайнем случае пропущенная обработка файлов или зависание клиента, использующего неверную модель повторов.

**Исправление:** состояние перечисления на открытом объекте/handle с generation, mask, real/overlay cursor и дедупликацией всего прохода; корректный сброс на restart и освобождение на close/duplicate. Конец возвращать только после исчерпания обоих источников. Тестировать маленький буфер, single-entry, несколько страниц, hidden-only промежуточную страницу, пустую реальную директорию и retained mask.

Контракт: [Microsoft: NtQueryDirectoryFile](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntquerydirectoryfile).

### C02 — P2: TLS-утечка соединений со временем исчерпывает все IPC handler slots

**Уверенность: высокая.** `Box<PerThread>` вместе с `SyncClient` намеренно не освобождается при завершении нити (`ipc_client.rs:31`, `ipc_client.rs:73`). Следовательно, pipe handle остаётся открытым до завершения **процесса**. Утечка ограничена числом когда-либо обслуженных нитей, а не текущим количеством нитей. Server удерживает один из 128 permits на всё время соединения (`pipe_server.rs:935`, `pipe_server.rs:969`) и блокируется на `read_exact` (`pipe_server.rs:1419`). Проверка liveness относится к процессу, который может жить ещё часы.

**Воздействие:** обычный thread churn способен остановить обслуживание новых клиентов/потомков. При соединении с живым, но молчащим server `SyncClient::send` ждёт без deadline (`ipc/src/lib.rs:333`); счётчик восьми IPC failures не растёт, пока вызов не вернулся. Поэтому «гарантированно умрёт через ~72 s» для зависшего обмена неверно: это лишь retry budget установления соединения.

**Исправление:** явный lifecycle соединений — подходящий destructor/FLS callback либо ограниченный пул с корректным владением; timeout/cancel для состоявшегося запроса и чтения body; supervisor shutdown должен завершать принадлежащие ему IO. Проверить легитимный churn >128 нитей с малым числом одновременно живых нитей. Это не повод запускать искусственную нагрузку на рабочей машине в ходе ревью.

### C03 — P2: e491803 исправил resolver пустого имени, но не passthrough потребителя

**Уверенность: высокая.** `resolve_for_hook` теперь выдаёт путь RootDirectory при пустом ObjectName (`hooks.rs:414`, `hooks.rs:456`). Однако `HookedAttrs::copy_passthrough_inner` раньше использования `pre_resolved_abs` отказывает при `ObjectName=NULL`, `Buffer=NULL` или `Length=0` (`hooked_attrs.rs:204`). Для passthrough пути это превращается в `STATUS_ACCESS_DENIED` (`fs_hooks.rs:389`).

**Воздействие:** объявленный fix работает на CoW redirect-ветке, но аналогичное открытие каталога в project_root/явном passthrough остаётся сломанным. Проверка только resolver не доказывает исправление `remove_dir_all` во всех поддерживаемых областях.

**Исправление:** helper должен принимать уже захваченный корректный абсолютный путь без повторного требования непустого исходного имени; добавить точечный full hook/E2E сценарий в passthrough-каталоге.

### C04 — P2: CoW materialization и его кэш не имеют атомарного жизненного цикла

**Уверенность: высокая в гонках и stale-ветках.** `prepare_overlay` делает `exists`→`copy`, игнорируя результат (`hooks.rs:1327`), mock — `exists`→`write` (`hooks.rs:1382`). Две нити/два процесса могут одновременно пройти проверку отсутствия: второй copy/write затем перетрёт уже начатые изменения первого. Read-side может увидеть частично копируемый overlay. Ошибка copy может превратиться в успешный последующий create с потерей исходного содержимого.

Индекс записывается до действительного open (`fs_hooks.rs:487` против `fs_hooks.rs:514`), даже когда open позже завершается ошибкой. `Cow` считается «стабильным» для локального cache (`hooks.rs:333`), но удаление overlay соседним процессом меняет его смысл: cached Cow с отсутствующим physical target попадает в fallback на реальный файл (`fs_hooks.rs:450`), не перечитав свежий whiteout. Это способ увидеть удалённый в merged view файл, а не доказательство bypass независимого deny-правила.

**Исправление:** атомарная публикация materialized объекта, согласованное locking/ownership по виртуальному пути и обработка copy/open ошибок. Индекс/whiteout должны иметь определённые состояния preparing/ready/deleted либо эквивалентный транзакционный протокол. Инвалидация необходима между процессами и для Cow, а не только локально для Passthrough/Hidden.

## Риски и вопросы, которые требуют отдельного воспроизведения

### R01 — P1: RWX trampoline и оставшийся код в static

**Кодовый факт подтверждён:** `alloc_near` выделяет 4 KiB `PAGE_EXECUTE_READWRITE` (`memory_guard.rs:1667`), manual detour использует небольшую часть страницы и не переводит её в RX после установки (`memory_guard.rs:1718`, `memory_guard.rs:1768`). Guard специально разрешает эти allocations в install window (`memory_guard.rs:1148`). Watch сохраняет только два первых байта записанных detours (`memory_guard.rs:686`), не целостность всей trampoline.

**Гипотеза воздействия:** после установки `static` эти уже существующие RWX-страницы пригодны для записи/исполнения гостевого кода без новой allocation/protect операции. Не проверялось, как конкретный Windows build обращается с ранее выданными RWX permissions при установке DynamicCodePolicy; это надо измерить. Даже при блокировке такого пути остаются code-reuse переходы на syscall instructions внутри доверенных модулей и дефекты S01–S06.

**Рекомендация:** trampoline после подготовки делать RX; не хранить рядом writable данные; проверять фактические permissions и защиту после bootstrap. Отдельно тестировать reuse существующего кода, а не только генерацию нового. Не описывать `static` как доказанно syscall-proof.

### R02 — P1: PID==0 всё ещё ошибочно понимается как «invalid handle, ядро откажет»

`foreign_write_decision(0,...)` возвращает Passthrough (`memory_guard.rs:1558`); аналогичные варианты есть в allocate/protect/unmap (`memory_guard.rs:1163`, `memory_guard.rs:1283`, `memory_guard.rs:784`). Но `GetProcessId` требует query-права и может вернуть 0 для handle, у которого есть права на мутацию, но нет query. Это документированный failure mode, а не доказательство недействительности handle.

**Уверенность:** высокая в ошибочном допущении, средняя в независимом escape: нужен доступный путь получения/наследования соответствующего foreign handle, не заблокированный proc/token/inject guards. Исследовать `DuplicateHandle`, наследование уже открытых handles и transient probes. Локальный tracker также всё ещё доверяет membership при `create_time==0` (`process_tracker.rs:200`), хотя launcher gate теперь fail-closes этот sentinel.

**Рекомендация:** unknown identity → deny для опасной операции; права инъектора отделить от гостевых. [Microsoft: GetProcessId](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocessid).

### R03 — P1/P2: защита completion event не скрывает сырой directory buffer

Kernel пишет перечисление прямо в guest `file_information`/IOSB; отдельная гостевая нить может наблюдать их до post-filter независимо от replacement event (`dir_filter.rs:1188`). IOCP completion также не маршрутизируется через private output buffer. Доступность такого race и его практическое использование здесь не воспроизводились.

**Воздействие:** утечка имён `.winrsbox`/whiteout entries; само по себе не получение их содержимого и не host-write. **Рекомендация:** при обещании скрытия брать private output/IOSB и публиковать только filtered результат; совместно проверить event/APC/IOCP семантику и lifetime. Постобработка guest-owned памяти — не confidentiality boundary.

### R04 — P1: внешние brokers и UI не закрыты структурно

Named pipes в целом разрешены, кроме denylist (`hooks.rs:1147`); COM/ALPC/shell guards перекрывают известные activation vectors. Но внешнему пользовательскому broker-процессу можно потенциально поручить работу/запуск по его собственному протоколу. Такой процесс не наследует Job вызывающего клиента. Конкретный внешний broker в этом аудите не выбирался и не эксплуатировался; отсутствие полного IPC namespace isolation уже признано THREATMODEL.

UI теперь перехватывает и `win32u!NtUserSendInput` (`ui_guard.rs:172`), поэтому старое замечание только про этот sibling закрыто. Однако все Job UI flags по умолчанию выключены (`jobctl.rs:80`), общая desktop/session остаётся общей. Denylist отдельных user32 entrypoints не равна изоляции окон, clipboard и session brokers.

**Рекомендация:** для headless-агента отдельные security identity и desktop/window station плюс политика доступа к IPC. Один private desktop сам по себе не создаёт отдельный namespace произвольных named pipes. Для произвольного враждебного нативного кода рассмотреть OS-enforced файловую границу с broker либо отдельную VM; выбор зависит от требуемой совместимости.

### R05 — P2: лимиты IPC ограничивают входной frame, но не все ресурсы launcher

64 MiB inflight budget резервирует только объявленный входной frame (`pipe_server.rs:1425`). Декодированные структуры, построенные ответы и `encode_to_vec` живут сверх него; проверка размера ответа происходит после кодирования (`ipc/src/lib.rs:260`). `OverlayChildren` может сформировать очень большой ответ. `child_pids` — неограниченная `SegQueue` (`main.rs:592`), а IPC принимает повторные/поддельные registrations. Логи и registry overlay не имеют общего byte/disk budget. Настройки Job ограничивают при желании лишь память отдельного процесса (`jobctl.rs:10`), без общего memory/CPU/process-count/time budget; launcher в бюджет гостевого Job не входит.

**Уверенность:** высокая в отсутствии end-to-end лимита; фактическое потребление не измерялось. **Рекомендация:** разные caps для путей, payload, ответов, children, log/disk, deadlines; streaming/pagination для больших listings; суммарные Job memory/process/CPU/time ограничения. Парсер bincode использует `standard()` без decoder limit (`ipc/src/lib.rs:282`); отдельный bounded-decoding/fuzz проход должен проверить расход памяти по hostile length fields. Конкретная allocator-exhaustion эксплуатация bincode этим ревью не заявляется.

## Политика по умолчанию и готовность для агента

Следующие ограничения в основном являются осознанной политикой, но существенно влияют на обещания продукта:

- Чтение вне проекта по умолчанию разрешено. Очистка env не скрывает `.ssh`, git credentials, файловые API tokens и другие секреты пользователя. При network-off гость может передать всё доступное ему наружу обычными API.
- Запись в `.cargo`, `.rustup`, некоторые npm/Python caches, `.claude`, `.config` разрешена passthrough (`sandbox.rs:118`, `sandbox.rs:168`). Эти деревья содержат также исполняемые инструменты, startup/config-файлы и поведение последующих несандбоксированных запусков. Это намного шире разрешения на безопасный download cache. Установленный winrsbox получил отдельные deny, остальной toolchain остаётся доверенным через writable filesystem.
- Внутри project_root любые policy rules проигрывают раннему passthrough (`decide.rs:1021`): нельзя одним deny защитить проектный secret или сами бинарники sandbox, если они лежат там. Refusal self-install проверяет только `project/node_modules` (`sandbox.rs:859`), а не произвольное расположение собственных binaries внутри project tree.
- `workreg` policy backend умеет overlay, но runtime read-side ещё не подключён. «Installers с registry CoW» нельзя считать общим поддержанным сценарием; сейчас часть операций сознательно отказывает.
- Job Object — сильная полезная основа для жизненного цикла: breakaway flags не включаются, kill-on-close есть. Но Job не запрещает запись в файловую систему и не привязывает WFP APP_ID к своим членам.

Практический статус: экспериментальные интерактивные запуски знакомого toolchain — возможны с учётом дефектов; автономный агент с секретами пользователя и произвольными dependency scripts — пока не готов; одновременные независимые проекты — сначала исправить S07; `static` — полезное усиление, не замена исправлениям и не доказательство полной изоляции.

## Где снизить сложность и аллокации

Числа ускорения не приводятся: текущих измерений нет. Исторические цифры из `winrsbox/docs/PERFORMANCE.md` относятся к другой реализации и не доказывают latency/overhead этого HEAD. Ниже — прослеживаемые затраты и предполагаемые улучшения, с условиями сохранения security.

## Проверки, необходимые перед заявлением готовности

CI сейчас собирает весь workspace, но исполняет `cargo test --workspace --lib --bins`, исключая integration tests (`.github/workflows/ci.yml:39`). В `real_world.rs:2` тесты объявлены ignored. В истории уже есть исправления базовых поломок CoW, device IO, static bootstrap и teardown после большого hardening-пакета. Это свидетельство разрыва проверки итогового поведения, а не основание доверять количеству unit-тестов.

Особенно показательные неверные oracle: тесты явно закрепляют MAXIMUM_ALLOWED→read и Cow+KEY_READ→real create. Структурный тест с поиском строки в исходнике и pure predicate test не проверяют, какие реальные права получил handle или какой файл/ключ изменился на хосте.

Минимальные критерии приёмки исправлений:

1. Для S01–S05, S07, S13 — внешняя проверка состояния хоста отдельным доверенным процессом, а не чтением из той же песочницы; проверять ACL/granted rights, содержимое, metadata, отсутствие внешних mutations.
2. Для потомков — чистый env, forged pipe/DLL, разные case guard, `CREATE_SUSPENDED`, запись родителем в child bootstrap и отказ LoadLibrary. Проверять реальное присутствие и работоспособность всех обязательных guard перед guest code.
3. Для scanner — page-rounding, несколько executable sections, участок после 64 MiB, альтернативная instruction boundary, existing code reuse, no-access/guard pages, concurrent protect/write. Нужен позитивный JIT-контракт, чтобы усиление не вернуло падения обычного Node/.NET.
4. Для listing/CoW — маленькие буферы и несколько страниц, single-entry, retained wildcard, restart, async event/APC/IOCP, concurrent create/delete/rename, два процесса и два проекта с одинаковым basename, ошибки копирования и диска.
5. Для сети — включённая policy на root и разноимённых потомках через разные socket API; одновременно работающий несандбоксированный процесс того же executable должен сохранять свою сеть. Ошибки WFP должны давать заявленный результат tier.
6. Для производительности — один фиксированный commit/profile, реальная операция и подтверждённый свежий launcher/hook; считать allocations/bytes, IPC/transactions/stats, directory entries processed, p50/p95 latency и peak memory. Масштабировать размер набора данных, а не создавать бессмысленную CPU-нагрузку. Отдельно измерять cold/warm и многопроцессность.

## Рекомендуемая очередность

1. Закрыть S01–S04 и S07; устранить сломанные security oracle. Это реальные доверительные границы, необходимые независимо от позиции по direct syscalls.
2. Исправить S06, S08–S10 и S13; синхронизировать документацию tiers с фактически установленной защитой. Принять отдельное архитектурное решение, требуется ли выдерживать произвольный враждебный native code.
3. Исправить C01–C04, включить адресные runtime acceptance tests в CI и обновить проверенный source pin в релизном процессе.
4. Оптимизировать directory state/index, CoW publication и IPC lifecycle; затем snapshot rules, shared cache data, scan buffer/boolean path и hot-stats. Для каждого изменения сверять не только время, но и сохранение изоляции и merged-view семантики.

Отчёт не утверждает отсутствия других уязвимостей. Уже найденных кодовых механизмов достаточно, чтобы отложить использование текущего снимка как самостоятельной песочницы для недоверенного кодер-агента.
