# R04 — внешние brokers и UI не закрыты структурно

Статус: **открыт, требует решения пользователя перед реализацией**. Не код-патч —
архитектурный компромисс объёма/совместимости.

Источник: `docs/review-xa-2026-09-20.md`, раздел «R04 — P1: внешние brokers и UI
не закрыты структурно» (риск, конкретный внешний broker в аудите не выбирался
и не эксплуатировался). Задача в TaskList: #77.

## Находка (из ревью, дословно переформулирована)

Named pipes в целом разрешены, кроме denylist; COM/ALPC/shell guards
перекрывают известные activation vectors. Но внешнему пользовательскому
broker-процессу можно потенциально поручить работу/запуск по его собственному
протоколу — такой процесс не наследует Job вызывающего клиента. Отсутствие
полного IPC namespace isolation уже признано в THREATMODEL.

UI-хуки перехватывают `user32!SendInput` и `win32u!NtUserSendInput`, но все Job
UI restriction flags по умолчанию выключены, а desktop/window station остаются
общими с хост-сессией. Denylist отдельных user32 entrypoints — это не
изоляция окон, clipboard и session brokers.

## Что уже сделано (проверено в текущем коде, не переносится из ревью бездумно)

Часть смежных находок этого же ревью уже закрыта в этой сессии и снижает
периметр R04, но не отменяет его:

- `crates/winrsbox-hook/src/ipc/alpc_guard/`, `com_guard.rs`, `shell_guard/`,
  `core/hooks/denylist.rs` — COM/ALPC/WMI activation-порты и CLSID
  заблокированы всегда (не опционально), включая fail-stop при попытке
  выйти за пределы known-safe broker-путей (коммиты `106e7b7`, `8c9ddd5`,
  вне периметра review-xa, из более раннего аудита).
- `crates/winrsbox-hook/src/system/ui_guard.rs` — `user32!SendInput` и
  `win32u!NtUserSendInput` перехвачены симметрично (закрывает старое
  замечание "только один sibling").
- `crates/winrsbox-launcher/src/contain/jobctl.rs::UiRestrictions` — полная
  инфраструктура для всех 8 `JOB_OBJECT_UILIMIT_*` флагов уже реализована и
  подключена (`sandbox/mod.rs::setup_job_object`), с `--strict-clipboard`
  как частичным opt-in (`no_read_clipboard`/`no_write_clipboard`).

**Подтверждено кодом (2026-09-22): все 8 флагов по-прежнему `false` по
умолчанию** (`UiRestrictions::default()`), с точным эмпирическим
обоснованием на каждый бит:

| Флаг | По умолчанию | Почему выключен |
|---|---|---|
| `UILIMIT_HANDLES` (0x01) | off | ломает кросс-процессные broadcast типа `WM_INPUTLANGCHANGE` (Alt+Shift/Win+Space переключение раскладки); anti-injection роль уже закрыта `ui_guard` на уровне user-mode |
| `UILIMIT_READ/WRITECLIPBOARD` (0x02/0x04) | off (кроме `--strict-clipboard`) | в связке с DESKTOP/EXITWINDOWS ломает кросс-процессный paste |
| `UILIMIT_SYSTEMPARAMS` / `DISPLAYSETTINGS` (0x08/0x10) | off | та же связка, что ломает paste; эффект без связки — мелкая UX-неприятность, не vector побега |
| `UILIMIT_GLOBALATOMS` (0x20) | off | ломает `RegisterWindowMessage`/`WM_INPUTLANGCHANGEREQUEST`; atom table не пересекает границу job |
| `UILIMIT_DESKTOP` (0x40) | off | эмпирически ломает paste из несандбоксированных приложений в sandboxed wezterm-gui; `SwitchDesktop` не значимый escape для интерактивных сессий, где пользователь уже перед экраном |
| `UILIMIT_EXITWINDOWS` (0x80) | off | бисекцией найден как блокирующий кросс-процессный `GetClipboardData`; logoff/shutdown защита уже переопубликована в user-mode хуком на `ExitWindowsEx` |

Т.е. это не забытая настройка — каждый флаг сознательно оставлен off с
задокументированной эмпирической причиной (в основном: связка ломает
clipboard paste между sandboxed и не-sandboxed процессами). Включение любого
без переоценки этой связки — реальный риск регрессии UX, а не просто
"включить и проверить".

## Что остаётся открытым (в этом коде не тронуто вообще)

1. **Private desktop / window station.** Ни один код в репозитории не
   создаёт отдельный `HDESK`/`HWINSTA` для sandboxed-процесса. Один private
   desktop сам по себе **не создаёт изолированный namespace для произвольных
   named pipes** — ревью прямо предупреждает не выдавать это за полный фикс.
2. **IPC namespace isolation для произвольных named pipes.** Текущая модель —
   allow-by-default с denylist известных плохих объектов (COM/ALPC/WMI), а не
   allowlist доверенных brokers. Гость может открыть произвольный named pipe
   стороннего процесса, который не наследует Job вызывающего клиента —
   отдельная identity/protocol такого broker вне периметра kernel Job и вне
   периметра ui_guard.
3. **Отдельная security identity для headless-агента.** Ревью прямо
   рекомендует это как часть решения — в коде это не начато.

## Компромисс, который называет ревью (дословно)

> Для headless-агента — отдельная security identity и desktop/window station
> плюс политика доступа к IPC. Для произвольного враждебного нативного
> кода — OS-enforced файловая граница с broker либо отдельная VM; выбор
> зависит от требуемой совместимости.

Это осевой выбор объёма:

- **Дёшево сейчас, ограниченная гарантия:** включить конкретные Job UI
  restriction flags там, где эмпирически подтверждено отсутствие регрессии
  (например `no_exit_windows`/`no_desktop` только для чисто headless-запуска
  без интерактивного terminal UI), плюс private desktop/window station для
  headless-режима. Не закрывает IPC namespace isolation для named pipes —
  нужно явно не выдавать это за полный фикс R04.
- **Дорого, полная гарантия для headless:** отдельная security identity
  (ограниченный токен/AppContainer или отдельный OS-пользователь) + private
  desktop/window station + allowlist-политика для IPC (вместо текущего
  denylist) — совместимость с интерактивными toolchain-сценариями (тот
  workflow, который сейчас в приоритете у проекта) вероятно пострадает или
  потребует отдельного режима запуска.
- **Максимальная гарантия для произвольного враждебного кода:** OS-enforced
  файловая граница с dedicated broker-процессом, либо отдельная VM
  (Hyper-V/WSL2-класс изоляции) — выходит за рамки текущей in-process
  hook-архитектуры winrsbox целиком; отдельный продукт-режим, не патч.

## Почему это не самостоятельный код-патч

Приёмка задачи в TaskList (#77) требует **письменного резюме
(этот документ) до того, как код пойдёт дальше явно безопасного ужесточения
Job UI flags** — то есть даже частичное включение флагов должно сначала
пройти through проверку "не сломает ли это интерактивный workflow, который
сейчас в приоритете", а не применяться молча по списку из таблицы выше.
Выбор между "дёшево сейчас" и "дорого, полная гарантия" — компромисс
объёма и совместимости, который явно называет ревью, и который должен
принять пользователь, а не быть выбран автономным агентом.

## Открытые вопросы для решения

1. Нужен ли headless-режим (без интерактивного terminal UI) как отдельный
   режим запуска — если да, `no_desktop`/`no_exit_windows`/`no_foreign_handles`
   становятся безопасно включаемыми именно в этом режиме, без риска для
   интерактивного пути.
2. Стоит ли инвестировать в private desktop/window station сейчас, зная, что
   это не закрывает IPC namespace isolation само по себе — или отложить до
   отдельного решения по broker allowlist.
3. Целевой уровень изоляции для "произвольного враждебного нативного кода"
   (не просто известного toolchain) — если он в объёме проекта, in-process
   hook-архитектура структурно не может дать эту гарантию в одиночку, и
   вопрос переходит в плоскость "отдельная VM/broker-процесс" — это другой
   продукт-режим, не итеративный патч текущей архитектуры.
